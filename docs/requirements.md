# Mend 要件定義書（MVP）

Nov 19, 2026

## 1. 概要

Mendは、AIが出力したHTMLを独自形式に変換せず、そのまま編集するエディタである。最大の要件は「編集していない部分はソースが1バイトも変わらないこと」（ソース同一性・レベルB）。

- **目的**：AI出力HTMLの文言修正を、構造・CSS・属性・コメント・インデントを壊さずに行う
- **Shitateとの違い**：Shitateは正式ドキュメント作成用（TipTapのスキーマに正規化する）。本ツールはGridなど複雑なレイアウトを含む任意のHTMLを、そのまま扱う別ツール
- **基本思想**：元のHTML文字列を唯一の正本とし、ブラウザ上のDOMは「表示」と「変更検知」にだけ使う。保存時は変更箇所だけをソース文字列にパッチとして書き戻す
- **MVPの範囲**：テキスト修正のみ。以降、段階的に操作を拡張する

## 2. 前提・決定事項

MVPはChrome/Edge向けWebアプリとして作り、デスクトップ化は最後に行う。

| 項目 | 決定内容 | 備考 |
| --- | --- | --- |
| ソース保持レベル | レベルB（未編集部分はバイト一致） | インデント、属性順、コメント、実体参照表記も維持 |
| 提供形態 | Webアプリ先行 → 後でデスクトップ化 | Electron/Tauriは未定。PDF化は現時点で不要 |
| 技術構成 | React + Vite + TypeScript + pnpm（モノレポ） | Shitateと揃える（確定） |
| 対象ブラウザ | Chrome / Edge のみ | File System Access APIを前提にできる |
| 入力HTML | CSS内包の1ファイルHTMLが中心、JavaScriptを一部含む | 編集中はスクリプト無効 |
| 保存 | 上書き保存と別名保存を選択可 | 差分表示は不要 |
| 履歴管理（将来） | 内部Gitでローカル履歴管理 | アプリ専用領域で管理し、ユーザーにGitを意識させない |
| デスクトップ化の判断材料 | WebKit（Safari）での編集挙動を検証してから決める | TauriはmacOSでWebKitを使うため |

## 3. アーキテクチャ

pnpmモノレポで、実行環境に依存するのはファイル操作だけにする。ElectronかTauriかは、apps/desktop を足すときに決めればよい。

図の内容（データフロー）：

1. ① 開く（apps/web）：`FileAdapter.open` でファイルを読み込み、ソース文字列を得る
2. ② 解析・対応表づくり（packages/core）：parse5で位置情報付きに解析し、文字位置の対応表を作る
3. ③ iframe 表示（packages/editor）：ソースを blob URL で読み込み、sandbox・スクリプト無効・designMode で表示する
4. ④ 編集の受け付け（packages/editor）：構造ガード・IME・Undo/Redo。変更されたテキストノードを core に渡す
5. ⑤ パッチ生成・保存前検証（packages/core）：変更箇所だけをソースに書き戻し、再解析して一致を確認する
6. ⑥ 書き込み（apps/web）：検証済みの新ソースを `FileAdapter.save` で書き込み、`onAfterSave` を呼ぶ（将来のGit用）

①〜⑥の順にデータが流れる。⑤がレベルBの要で、ここを通らない保存はない。

```
packages/core     解析、対応表、パッチ生成・適用、保存前検証（Vitestで単体テスト）
packages/editor   iframe表示、構造ガード、IME対応、Undo/Redo（PlaywrightでE2Eテスト）
apps/web          Reactの画面、Web版FileAdapter
fixtures/         テスト用HTML一式（7.2）
```

実行環境ごとに差し替えるインターフェース：

```ts
interface OpenedFile {
  name: string
  source: string          // 読み込んだバイト列をUTF-8でデコードしたもの
  lastModified: number
}

interface FileAdapter {
  open(): Promise<OpenedFile>
  save(file: OpenedFile, source: string): Promise<OpenedFile>
  saveAs(source: string, suggestedName: string): Promise<OpenedFile>
}

// 将来：アプリ専用領域でのGit履歴
interface HistoryAdapter {
  commit(fileKey: string, source: string, message: string): Promise<void>
}
```

UTF-8のBOMは読み込み時に有無を記録し、保存時にそのまま戻す（AC-01のバイト一致のため）。

## 4. MVP機能要件

MVPは「開く、文字を直す、保存する」の3つで完結する。

### 4.1 ファイル操作

| ID | 機能 | 内容 |
| --- | --- | --- |
| F-01 | 開く | `showOpenFilePicker` でHTMLファイルを開く。ドラッグ＆ドロップにも対応。UTF-8を厳密にデコードし、不正なバイト列があれば開かずに理由を表示する（Shift\_JISなどUTF-8以外の可能性にも触れる）。BOMの有無を記録し、保存時にそのまま戻す |
| F-02 | 上書き保存 | 開いたファイルハンドルに `createWritable` で書き込む。Ctrl+S |
| F-03 | 別名保存 | `showSaveFilePicker` で新しいファイルに保存。以降の上書き先は新ファイルに切り替える。Ctrl+Shift+S |
| F-04 | 未保存警告 | 未保存の変更がある状態で閉じる・別ファイルを開くときに確認する。タイトルに変更有無を表示 |
| F-05 | 外部更新の検知 | 保存前にファイルの更新日時を確認し、開いた後に外部で変更されていたら警告する |
| F-06 | 最近開いたファイル | ファイルハンドルをIndexedDBに保存し、起動画面にファイル名と最後に開いた日を表示する（フォルダのパスは取得できないため表示しない）。開き直すときは改めて権限を求める |

### 4.2 表示

| ID | 機能 | 内容 |
| --- | --- | --- |
| V-01 | 編集ビュー | 元HTMLをsandbox付きiframeに表示。スクリプトは実行しない。CSSは元のまま効かせる |
| V-02 | プレビュー | スクリプトを有効にした読み取り専用表示。編集ビューとタブで切り替える。表示内容は「現在のパッチ適用後ソース」 |
| V-03 | 編集可能範囲の明示 | ホバーで編集できるテキストの元要素を薄く強調。編集対象外（script/style等）は反応しない |
| V-04 | 変更箇所の強調 | 保存前の変更済みテキストと検索結果を強調する。CSS Custom Highlight API（スタイルはiframeのadoptedStyleSheetsで与える）で描画し、DOMのノードを増やさない。ホバー時の枠と要素名のラベルは親ページ側の重ね合わせ層で描く |

### 4.3 テキスト編集

| ID | 機能 | 内容 |
| --- | --- | --- |
| E-01 | 文字の挿入・削除 | 既存テキストノード内での入力、BackSpace、Delete。日本語IMEに対応 |
| E-02 | 構造変更のブロック | Enter（段落分割）、要素をまたぐ削除、装飾ショートカット（Ctrl+B等）、D&Dを無効化または巻き戻す。ただし改行が表示される要素（`white-space: pre` / `pre-wrap` / `pre-line` / `break-spaces`）の中では、Enter と Shift+Enter でテキストに改行文字を入れる。それ以外では Shift+Enter で `<br>` を入れる（E-07） |
| E-03 | 貼り付け | プレーンテキストとして挿入。改行はスペースに置換（MVPでは改行で要素を増やさない）。改行が表示される要素の中では改行のまま入れる |
| E-04 | Undo / Redo | 自前の履歴（テキストノード単位の変更前後値）で実装。ブラウザ標準のUndoは使わない |
| E-05 | 検索 | Ctrl+Fでテキスト検索し、該当箇所へスクロール（置換は将来） |
| E-06 | 変更箇所一覧と個別の取り消し | 未保存の変更をテキストノード単位でサイドパネルに一覧表示（場所、変更前、変更後）。クリックで該当箇所へスクロールし、「この変更を戻す」でその箇所だけ元の文字列に戻す。取り消し自体もUndo履歴に積む |
| E-07 | `<br>` による改行 | 改行が表示されない要素の中で Shift+Enter を押すと、カーソル位置でテキストを分けて `<br>` を入れる。消せるのは自分で入れた未保存の `<br>` だけで、行頭の BackSpace・行末の Delete で前後の行をつなぐ。元のファイルにある `<br>` は消せない。書き方はファイル内の既存の `<br>` に合わせる（`<br />` など、なければ `<br>`）。保存すると入れた `<br>` はファイルの一部になり、保存前に入れた `<br>` は保存後に Undo で消せない（文字の修正は保存をまたいで Undo できる） |

### 4.4 保存処理

| ID | 機能 | 内容 |
| --- | --- | --- |
| S-01 | パッチ生成 | 変更されたテキストノードごとに、文字単位差分からソース上の置換範囲を求める |
| S-02 | パッチ適用 | オフセットの後ろから順に元ソースへ適用 |
| S-03 | 保存前検証 | 新ソースを再パースし、変更テキスト以外が元と一致することを確認。不一致なら保存を中止し内容を表示 |
| S-04 | 保存後フック | `onAfterSave(oldSource, newSource, meta)` を用意（将来のGitコミット用。MVPでは空実装） |
| S-05 | 保存後の再同期 | iframeは読み込み直さない。保存したソースを新しい正本として解析し、今のDOMと並行走査して対応表だけを張り直す（中身を全部消したテキストノードはDOMにだけ残るので読み飛ばす）。Undo履歴・スクロール位置・カーソル位置は保持し、保存をまたいでUndoできる（保存した `<br>` の挿入・削除は除く、E-07） |

## 5. 技術仕様の要点

レベルBを成立させる鍵は、「ブラウザDOMとparse5ツリーを一致させること」と「テキスト位置→ソース位置の正確な対応」の2点。

### 5.1 解析と表示の設定

- parse5：`parse(source, { sourceCodeLocationInfo: true, scriptingEnabled: false })`
  - `scriptingEnabled: false` は必須。スクリプト無効のブラウザと同様に `<noscript>` の中身を要素として解析させるため
- iframe：`sandbox="allow-same-origin"`（`allow-scripts` なし）。元ソースのバイト列から blob URL を作って読み込む
  - `srcdoc` は使わない。srcdoc の文書は doctype がなくても no-quirks モードになるが、parse5 は doctype なしを quirks モードで解析するため、木（例：`<p>` の中の `<table>`）も表示もずれる。blob URL なら両方とも quirks モードになり、ファイルを直接開いたときと同じ表示になる
  - ソースへの `<base>` 挿入や属性付与など、正本を改変する前処理は行わない
  - iframe が `<meta http-equiv="refresh">` などで別ページへ遷移した場合は、検知して読み込み直す
- 編集の有効化は `iframeDoc.designMode = 'on'` を使う（`contenteditable` 属性をDOMに付けない）
- 前提の技術検証：sandbox（`allow-scripts` なし）の下で designMode、親ページから登録したイベント、`getTargetRanges()` が動くことを、実装の最初に確認する。動かない場合の代替案：`allow-scripts` を付け、iframe の `csp` 属性で `script-src 'none'` を指定する

### 5.2 ノード対応表

- parse5ツリーとiframeのDOMを `childNodes` 順に並行走査し、`WeakMap<Text, TextRecord>` を作る
- `TextRecord` = ソース上の `startOffset` / `endOffset`、元のデコード済み文字列、位置対応表（5.3）
- 走査中にノード種別・タグ名が食い違ったら、読み取り専用で開き警告を出す
- 編集対象外：`<head>` 内、`<script>` `<style>` `<template>` `<textarea>` の中身、空白のみのテキストノード、svg・math要素の中、option要素、button要素の中（SVG内の文字は将来の編集対象の候補）

### 5.3 テキスト位置とソース位置の対応

デコード後の1文字が、ソース上では複数文字になるケースをすべて扱う。

| ケース | ソース | DOM |
| --- | --- | --- |
| 名前付き実体参照 | `&amp;` `&nbsp;` | `&` U+00A0 |
| 数値文字参照 | `&#12354;` `&#x3042;` | `あ` |
| セミコロンなしの旧式参照 | `&amp` `&copy` | `&` `©` |
| 改行の正規化 | `\r\n` / `\r` | `\n` |
| サロゲートペア（絵文字など） | 1文字 | UTF-16で2単位 |

- 各テキストノードについて「DOM上のUTF-16位置 → ソース上の \[start, end)」の配列を作る（`entities` パッケージ等でトークン単位にデコード）
- 対応表から復元した文字列が parse5 の `node.value` と一致しないノードは編集不可にする（安全側に倒す）

### 5.4 編集の受け付け（構造ガード）

「事前に止める」と「事後に巻き戻す」の二段構えにする。

1. **事前防止（`beforeinput`）**
   - `insertParagraph` `insertLineBreak` `format*` `insertFromDrop` `deleteByDrag` は `preventDefault`（改行が表示される要素では改行文字を、それ以外の `insertLineBreak` では `<br>` を自前で入れる。E-02、E-07）
   - 自分で入れた `<br>` で分けたテキストは、1つのテキストノードの「行」として扱う。対応表・構造ガードは、その `<br>` と次の行のテキストノードを元の構造の一部とみなす
   - 中身が空の行（`<br>` の直後）には、DOM上だけゼロ幅スペース（U+200B）を置く。行末の `<br>` の後ろは表示上の位置がなく、Chrome がカーソルと入力を `<br>` の前に移すため。保存・変更一覧・Undoの値には含めない
   - `insertFromPaste` は止めて、プレーンテキストを自前で挿入
   - 削除系は `getTargetRanges()` を見て、範囲が複数ノードにまたがる場合は止める
   - テキストノードを空にする削除は自前で `data = ''` にする（Chromeは空のテキストノードを消して `<br>` を入れるため）
2. **事後の巻き戻し（MutationObserver）**
   - 対応表にあるテキストノードの `characterData` 変更 → 受け入れ、変更済みにする
   - `childList` / `attributes` 変更 → MutationRecordを逆順に逆適用して元に戻し、カーソル位置を復元
   - 例外：境界での入力で新しいテキストノードが生まれた場合は、隣接する既存テキストノードへ統合してから除去
3. **IME**：`compositionstart`〜`compositionend` の間は巻き戻しを保留し、確定後にまとめて判定する

### 5.5 書き戻し時の文字の扱い

- 新しく入力された文字は `&` → `&amp;`、`<` → `&lt;` のみエスケープ
- 新しく入力された改行は、そのテキストノードの中、なければ直前、なければ直後にあるソースの改行コード（CRLF / LF / CR）で書き出す。どこにもなければ LF
- 新しく入力した文字が直前のソースとつながって別の文字参照に化ける場合（例：`&not` の直後に `in;` を入力すると `&notin;` になる）は、入力の先頭1文字を数値文字参照（`&#105;` など）で書き出す
- Chromeが自動挿入するU+00A0：新しく入力した文字に限り、単独なら通常スペースに戻し、連続スペースの場合のみ `&nbsp;` で出力する（`white-space: pre` 系の要素内ではそのまま）
- 元からあった文字は、変更範囲の中でも元の表記（`&nbsp;` など）をそのまま残す（5.6）

### 5.6 パッチ生成と適用

1. 変更済みテキストノードごとに、元の文字列と現在の文字列の共通接頭辞・接尾辞を除いて変更範囲を求める
2. 変更範囲の中でさらに文字単位の差分（Myers）を取り、変わっていない文字は元ソースの表記をそのまま使う。範囲の端は、文字参照とサロゲートペアの区切りに合わせる
3. 変更範囲を5.3の対応表でソース上の範囲に変換し、`{ start, end, text }` のパッチにする（Phase 2以降のタグ挿入や要素単位の置換にも使える汎用の形）
4. 全パッチを `start` の降順に並べ、範囲に重なりがないことを確認してから元ソースに適用する

### 5.7 保存前検証

新ソースを同じ設定で再パースし、元ツリーと並行走査する。

- ノード種別・タグ名・属性（名前、値、順序）・コメント・doctypeがすべて一致すること
- テキストは、未変更ノードは元と、変更ノードは書き戻しのルール（5.5）を適用した後の期待値と一致すること。中身を全部消したテキストノードは、再解析した木に存在しなくてよい
- パッチ範囲外のソース文字列が元と完全一致すること（構造上自明だがアサーションとして入れる）

### 5.8 Undo / Redo

- `{ textNode, before, after, selection }` の自前スタック。連続入力は一定時間（例：500ms）とIME確定単位でまとめる
- `beforeinput` の `historyUndo` / `historyRedo` と Ctrl+Z / Ctrl+Y を横取りして自前スタックを使う

* 履歴はソース上の位置ではなく「テキストノードと変更前・変更後の値」で持つ。保存しても履歴は消さず、保存をまたいでUndoできる（S-05）

## 6. 非機能要件・スコープ外

### 6.1 非機能要件

- **安全性（最優先）**：検証に失敗した状態では絶対に保存しない。迷ったら編集不可・保存中止の側に倒す
- **セキュリティ**：編集対象のHTMLに含まれるスクリプトをエディタの権限で実行しない。プレビューは `allow-scripts` のみ（`allow-same-origin` なし）で分離する
- **性能**：1MB程度のHTMLで、開くまで 1秒以内、入力遅延を体感させない、保存（検証込み） 1秒以内を目安とする
- **外部との通信**：Mend自体はサーバーと通信せず、ファイルの内容を外部に送らない。ただし、編集対象のHTMLが参照する外部リソース（CDNのCSS、Webフォントなど）は表示のために読み込む
- **テスト容易性**：`packages/core` はDOM非依存で、Vitestだけで単体テストできること

### 6.2 MVPのスコープ外

- インライン装飾、要素の追加・削除・移動、表の操作（例外：Shift+Enter による `<br>` の挿入、E-07）
- 属性（class、href、altなど）の編集
- スクリプトが生成する内容の編集（そもそもソースに存在しない）
- 外部CSS・画像など相対パス参照の解決（Web版では表示されないことがある）
- UTF-8以外の文字コード、置換、差分表示、Git履歴、デスクトップ化
- Chrome / Edge 以外のブラウザ対応

## 7. 受け入れ条件とテストHTML一式

中心となる条件は「任意のテストHTMLで、1箇所の文字を直して保存すると、`diff` にその箇所だけが出る」こと。

### 7.1 受け入れ条件

- [ ] AC-01：開いて何も編集せず保存すると、バイト列が元ファイルと完全一致する
- [ ] AC-02：テキストを1箇所修正して保存すると、差分はそのテキスト範囲内に収まる
- [ ] AC-03：実体参照の隣を編集しても、その実体参照の表記は変わらない
- [ ] AC-04：Enter、要素をまたぐ削除、装飾付き貼り付け、Ctrl+B、ドラッグで、DOM構造が変わらない（Shift+Enter は AC-12）
- [ ] AC-05：日本語IMEで変換・確定・キャンセルしても、入力結果が正しく保存される（自動テストに加え、docs/manual-tests.md の手順でMicrosoft IMEとGoogle日本語入力を手動確認する）
- [ ] AC-06：要素内のテキストを全部消しても、要素自体は残り `<br>` が挿入されない
- [ ] AC-07：編集中に元HTMLのスクリプトが一切実行されない（`alert` や `console.log` を含むテストで確認）
- [ ] AC-08：保存前検証に意図的に失敗させると（テスト用フック）、保存されず理由が表示される
- [ ] AC-09：Undo / Redoで編集前後を行き来でき、すべてUndoして保存すると元とバイト一致する
- [ ] AC-10：上書き保存・別名保存・未保存警告・外部更新の検知が仕様どおり動く

* [ ] AC-11：変更箇所一覧から1件だけ戻して保存すると、その箇所は元とバイト一致し、他の変更はそのまま残る
